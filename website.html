01
FLAGSHIP SYSTEM 500K+ DAILY TRANSACTIONS

Event-Driven, Multi-Tenant EV Charging Platform

Evolving a charge point management system from synchronous request chains to an event-driven microservice architecture on Kubernetes, sustaining 500K+ daily transactions at 99.9% availability.

Distributed Systems · Elocity · Kafka · Redis · PostgreSQL · EKS
01 · CONTEXT & CONSTRAINTS

Bursty Device Traffic Meets Synchronous Request Chains

The platform manages chargers, sessions, tariffs, payments, roaming, and fleets for many tenants across multiple deployment environments. Charger telemetry and session events arrive in bursts tied to driver behaviour, and early request paths performed validation, persistence, and payment checks synchronously.

Under peak load that coupling produced slow responses on hot endpoints and pressure on database connections — and a slow payment dependency could stall an unrelated charging flow.

02 · MY ROLE

Backend & Distributed Systems Lead

Owned service design and implementation for core backend modules in NestJS and TypeScript: authentication and RBAC, subscription billing, payments, and the event pipelines between charging, telemetry, and payment services. Worked hands-on through query tuning, caching, Kubernetes deployment, and production debugging, and set the code-review and reliability standards other engineers followed.

03 · DESIGN DECISIONS & TRADE-OFFS

06 · LESSONS
  • Asynchrony moves complexity, it does not remove it: Every queue added needs an idempotency story, a retry policy, and a way to see consumer lag.
  • Device traffic is not web traffic: Long-lived charger connections and bursty reconnect storms deserve their own capacity model.
  • Measure before tuning: The largest wins came from endpoints identified through profiling, not from the ones that looked expensive in code review.
02

EVLM — Greenfield Load-Management System on Shared Platform Foundations

0 → 1 Architecture · Utility Grid Control · ~3 Months to Production
CONTEXT & CHALLENGE

Coordinating Physical Chargers Against Transformer Limits

Utilities need to see transformer loading alongside aggregated EV charging demand and curtail charging before assets exceed thermal limits. That means reconciling high-frequency transformer readings with asynchronous charger telemetry, then issuing control commands to heterogeneous hardware — safely, and with a small team.

OWNERSHIP & ROLE

Architect & Hands-On Technical Lead

Led EVLM from scratch to production in roughly three months: service boundaries, Kafka pipelines, OCPP smart-charging profile schemas, data model, deployment on EKS, RBAC, and alert thresholds — while working through state-transition race conditions and charger protocol behaviour during integration.

KEY ARCHITECTURE DECISION

Reuse Mature Services; Isolate the New Control Path

  • Reused, not rebuilt: EVLM consumes the existing identity service (AMS) and proven charging-platform capabilities instead of duplicating authentication, tenancy, and charger connectivity.
  • Separate product boundary: Load-management logic lives in its own services so a fault in a greenfield control path cannot destabilise the mature charging platform.
  • Monitoring decoupled from dispatch: Telemetry ingestion and control dispatch are isolated so asset-protection evaluation stays deterministic when charger communication is slow.
  • Closed-loop verification: Every curtailment is dispatched as an OCPP charging profile (SetChargingProfile / ClearChargingProfile) and confirmed against subsequent telemetry rather than assumed.
  • Simulation before live control: Synthetic transformer load and mock OCPP exchanges were used to exercise overload, fallback, and error states before touching real hardware. AI coding tools accelerated scaffolding and test generation; design and correctness review stayed human.

03

Multi-Tenant Identity, Trust Boundaries & Platform Security Review

Security Architecture · Shared AMS · JWT · RBAC · PostgreSQL RLS
CONTEXT & CHALLENGE

One Identity Service, Many Products and Tenants

The Account Management Service handles authentication, JWT issuance, social OAuth, RBAC, and tenant management for both the charging platform and EVLM. As services multiplied, how each one verified identity and enforced tenant isolation had drifted.

OWNERSHIP & ROLE

Built Core Auth; Led the Platform Review

Built authentication and RBAC modules as a senior engineer, then inventoried roughly 25 repositories and Helm releases to map service ownership, trust boundaries, and documentation gaps, producing a prioritised hardening roadmap.

FINDINGS & RECOMMENDATIONS
  • Divergent token verification: Some services delegated RS256 signature checks to the Istio ingress gateway and trusted a forwarded x-jwt-payload header; EVLM verified tokens in-process. Recommended a single documented model and header-spoofing protections for in-mesh traffic.
  • Tenant isolation coverage: PostgreSQL row-level security policies existed, but many services relied on application-level tenant_id filtering instead. Recommended an RLS coverage assessment and consistent enforcement.
  • Operational gaps: Helm-declared services without matching repositories, no centralised OpenAPI specifications, and no backup and disaster-recovery runbook — each turned into a roadmap item with an owner.

04

Payment State Machines, Tariffs & Revenue-Share Billing

Financial Systems · Elocity · Correctness Over Convenience
CONTEXT & CHALLENGE

Money Moves Through Unreliable Networks

A charging session's price can combine energy (kWh), time-of-use rates, idle fees, and load-based dimensions, and the resulting revenue is split between operators and site hosts. Charger connectivity drops, webhooks retry, and payments must never be double-captured or silently lost.

OWNERSHIP & ROLE

Designed and Built the Billing Path

Built subscription billing and payment modules, and later led the redesign of payments and user management that enabled a 5× increase in concurrent sessions.

ENGINEERING HIGHLIGHTS
  • Explicit state machines: Payment and session states with defined transitions, so retries and late events resolve deterministically instead of overwriting each other.
  • Idempotency at the boundaries: Idempotency keys on payment operations and idempotent Kafka consumers so redelivery is safe.
  • Exact arithmetic: Integer and fixed-precision decimal maths for tariffs and revenue splits — no floating-point drift.
  • Reporting as a product: Revenue-share PDF exports and scheduled report subscriptions generated from the same ledger the billing engine writes.
OUTCOME
5× Concurrent sessions after payments & user-management redesign
05

Device Protocol Engine: OCPP 1.6 / 2.0.1 & OCPI Roaming

IoT & Protocols · Hardware Interoperability · Stateful Connections
CONTEXT & CHALLENGE

Physical Hardware Does Not Follow the Spec

Chargers from multiple manufacturers, on different firmware versions, connect over long-lived WebSockets. Payloads deviate from the specification, connections drop mid-session, and devices reconnect with stale state.

OWNERSHIP & ROLE

Protocol Design & Integration

Designed adapter boundaries that isolate core charging logic from vendor quirks, and worked through integration testing with physical chargers and an OCPP simulator.

ENGINEERING HIGHLIGHTS
  • Fault-tolerant session state machine: Reconciliation on reconnect so an offline event mid-charge resolves to a correct session and billing state.
  • Version translation: A message-translation layer between OCPP 1.6J and 2.0.1 so the core works with one internal model, including smart-charging profiles.
  • Security profiles: OCPP 1.6 security-profile behaviour, TLS, and certificate handling at the connection edge.
  • OCPI roaming: Token authorisation, session push, and CDR exchange with external e-mobility service providers.

02 ENGINEERING PRINCIPLES

How I Design & Ship Systems

The working method behind the systems above — from first measurement to the on-call rotation.

01
MEASURE

Start From Production Data

Profiles, query plans, consumer lag, and error logs decide where effort goes — not intuition about which code looks slow.

02
MODEL

Estimate Capacity & Failure Modes

Back-of-the-envelope throughput, storage, and connection estimates, plus an explicit list of what happens when each dependency is slow or down.

03
CONTRACT

Define Interfaces First

API schemas, event payloads, state transitions, and data ownership agreed before implementation, so teams can build in parallel.

04
SHIP

Deliver Incrementally & Reversibly

Small changes through GitOps pipelines, backward-compatible schemas, and rollouts that can be undone without a data migration.

05
OPERATE

Own It in Production

Dashboards, alerts, and runbooks ship with the feature. Incidents end with a blameless RCA and a tracked fix, not just a restart.

Engineering Principles

  • Boring where possible: Proven components and simple designs, with novelty spent only where the problem demands it.
  • Make failure explicit: Timeouts, retries, idempotency, and fallbacks are designed, not discovered in an incident.
  • Data ownership is architecture: Clear owners for every table and topic prevent most cross-team coupling.
  • Reliability is a feature: Throughput numbers mean little if the system degrades at peak.
  • Raise the floor: Reviews, standards, and mentoring compound faster than individual heroics.
